Part 1 — 问题与目标

用户人物 confirmed

一位 AI/agent 工程学习者，正在构建个人的技术情报系统。他不是在消费通用 AI 资讯，而是围绕一条明确学习路线（agent engineering / LangGraph / LangChain / tool-use / MCP / browser & computer-use agents / data agents / RAG 知识系统 / 生产评估）筛选高信号内容，并据此决定"现在学什么、存什么"。

使用场景

每天清晨，他不需要打开浏览器手动刷 HN / Reddit / 博客 / arXiv，而是收到一份当日高信号简报；当他在做深度研究或写作时，能直接问自己的知识库"我收集过关于 X 的内容吗"，并立刻得到带来源的结构化答案。

核心痛点

  • 输入窄：现有系统只采 GitHub Search + RSS（30 源），漏掉 Reddit 评论、Twitter/X、Telegram、HN 讨论等"人才有的 taste"信号。
  • 无背景无对话：条目只有单条 LLM 摘要，没有背景富化（enrich）与社区评论摘要，读一条仍要自己去翻原始讨论。
  • 资产不积累：产物是一次性 JSON 文件 + 每日简报，历史不沉淀为可检索、可关联的资产。
  • 质量门控粗：reviewer 对整批一条加权分一刀切（analyses[:5] 样本闸整批），单条质量差异被抹平。

需求层级（已确认）

层内容状态
表层需求停止手动盯信息源；原始链接 → 结构化条目；质量门控；主动送达confirmed
深层需求持续输入、避免遗漏；对资产有掌控感；信任库中每条值得读confirmed
根本需求信息过载的恐惧；身份诉求「从被动追赶趋势 → 主动塑造认知」confirmed

愿景 confirmed

认知复合引擎 (Cognitive Compounding Engine)

把系统从"AI 新闻阅读器"升级为"个人战略情报引擎"：系统性结构化信息、提炼战略洞察，并把每日高信号内容沉淀为可复用知识资产，最终加速所有者的认知迭代与决策。

需求证据

需求强度：高。源为用户自述的 TODO.md §thinking 史诗（含 7 个用户故事 + 价值主张 + 非功能需求 + 验收标准示例），非外部需求评估。所有者逐条确认后视为 accepted intent。

目标成果

为所有者，把每日情报采集从「仅 GitHub+RSS、单语、无评论/背景富化」改为「Horizon 全源雷达 + 富化条目持久化到可检索资产库」，以输入覆盖度与条目深度提升、且资产可复用为目标。

Part 2 — 方案概览

当前上下文（已实现，将被修改）

v0.7.0 现有链路 plan → collect → analyze → review → organize（LangGraph），产出 knowledge/articles/*.json + 每日邮件简报，检索面为 Flask UI（:5050）与 MCP（stdio）。本增量以 Horizon 替换 collect/analyze/digest 三段，新增资产落库，重写检索面。

目标业务流（核心逻辑，含决策点）

daily trigger │ ▼ [fetch] 并发拉取 N 类源（HN/Reddit/X/Telegram/GitHub/OpenBB/RSS/…） │ ▼ [dedup] 跨平台合并同一 story / URL │ ▼ [score] 按 profile 对每条打 0–10 分 + reason + summary + tags │ ▼ ┌──────────── score ≥ threshold? ────────────┐ │ 否 │ 是 ▼ ▼ [drop] 记录审计日志（audit） [enrich] 背景富化 + 评论摘要 │ │ ▼ ▼ END（不落库） [persist] 写入新资产库（可检索） │ ▼ [summarize] 双语简报（EN + 中文） │ ▼ [deliver] 邮件 + 可选飞书/webhook │ ▼ END

决策点：score ≥ threshold 决定条目进入富化/落库还是淘汰审计；两条分支均标注（是→富化链路；否→淘汰）。终端态：淘汰 END 与投递 END。另：AI 调用失败 / 源失败 / SMTP 缺失均为各自降级路径（见 Part 3），不改变主链。

信息架构

层职责归属
雷达层（Horizon）fetch / dedup / score / enrich / summarize / deliver外部参考实现 reference/Horizon，经 MCP 或直接调用
资产层（新库）持久化富化条目，提供检索（供 MCP/UI）本仓库自建（形态待技术设计）
消费层MCP 检索 + Flask UI 管理 + 简报邮件保留现有入口，D6 重写指向新库
关键结构决策：雷达用 Horizon 的，资产层用自己的——Horizon 不持久化知识实体（src/mcp 只存 run artifacts），资产积累、检索、可关联是你愿景的独有部分，必须自建。

旅程

① 自动情报采集：定时触发 → 全源 fetch → 打分 → 富化 → 落库 → 双语简报投递。
② 所有者消费：收简报 → 按分决定精读/略读 → UI 打开/编辑 → 资产沉淀。
③ Agent 查询：MCP search_articles / get_article / knowledge_stats → 结构化答案。

五态规格（仅对 UI/MCP 检索面与邮件简报适用）

状态检索面（UI/MCP）简报邮件
Initial空搜索栏 + 最新条目列表（默认按分数降序）不适用（无交互）
Trigger输入关键词 / 点击筛选 / get_article(id)定时触发
Success命中列表（标题/摘要/标签/分数/来源）邮件送达
Error库不可读 → 明确报错；旧字段 → N/A 而非崩溃SMTP 失败 → 打印 + exit 0（不静默）
Empty"无匹配"提示，不空白"今日无高优先级条目"短正文

管线（fetch/score/enrich/persist）为批处理作业，无初始/空 UI 态，五态不适用。

边界与恢复

  • 空状态：无高于阈值条目 → 库不变、报 0、不报错。
  • 依赖失败：源宕 / AI 宕 / SMTP 缺失 → 各自降级不致命。
  • 重复动作：重跑幂等，按 story/URL 去重不重复落库。
  • 陈旧状态：检索面不读旧 schema 字段（N/A 或移除）。
  • 边界输入：threshold=0 与 =10；max_items 上限生效；单源 quota=1 保底。
  • 恢复：AI 调用指数退避重试；源失败下次轮次重试。

非功能需求

维度要求
性能每日一轮在定时窗口内完成；检索命中响应即时（本地库规模，无需异步）
兼容Python 3.12+ / uv；MCP 走 stdio（Cursor/Claude/Codex/OpenCode）；UI 走 Flask :5050
容错单源失败 / 单条 AI 失败 / SMTP 缺失均不得中断整轮
分析见下表埋点
隐私检索 query 不落原始文本（可能含敏感词），仅记命中/计数或哈希
